## 功能开发：V13 相册枚举采集（已完成）

需求：给一个相册 ID，拿到该相册全部图片，每张随机间隔 3~10 秒下载，
主下载点失败自动切换线路/下载点。用户提供样例相册 `6aa113208a506`。

### 探测阶段的关键发现（决定了整个方案）
用真实请求验证，四个结论：
1. **该站不返回 404** —— 越界序号 `00057.jpg` 返回 `200 + text/html`，
   存在的 `00001.jpg` 返回 `200 + image/jpeg`。**存在性只能看 Content-Type**，
   看状态码会永不停止或第一张就误停。（此前那次 403 是探针头不对导致的误判）
2. **WAF 校验 Accept 头** —— 无 Accept 或 `*/*` → 403；含 `image/*` → 200；
   Referer 无影响。**这是项目级坑**：原 `build_headers` 只设 UA，
   所以项目对所有图片请求本来都会 403。
3. 直连可用，**无需登录、浏览器、代理**
4. 一张图有 4 个下载点：`.jpg` 原图 + `_1200x0/_800x0/_600x0.webp`
   —— 这就是用户说的"下载点切换"，站点自带，不用另找镜像

### 改动清单
- `backend/collectors/xchina/gallery.py`（新建）：parse_gid / probe(三态) /
  url_for / discover(连续 miss_stop 次停止) / XChinaGallerySpider，注册为 `xchina_gallery`
- `backend/core/database.py`：resources +mirrors 列；`add_resource` 接收 mirrors/size；
  新增 `get_mirrors()`（注意 sqlite3.Row 不支持 .get()）
- `backend/core/config.py`：DEFAULT_ACCEPT / IMAGE_ACCEPT 常量、
  domain_max_interval、mirror_fallback、probe_interval
- `backend/downloaders/base.py`：新增 `download_with_mirrors` + `_stream_one`
  （require_image 校验 Content-Type）+ `_swap_ext`；build_headers 补 Accept
- `backend/downloaders/ratelimit.py`：间隔支持随机区间 + `set_interval()`
- `backend/downloaders/image.py`：改用 download_with_mirrors
- `backend/core/task_manager.py`：`_crawl` 支持 log 回调；透传 mirrors/size
- `config.yaml`：domain_concurrency=1、间隔 3~10s、probe_interval=0.3、mirror_fallback
- 前端 `App.vue`：采集器中文名映射 + 按采集器切换输入提示
- `tests/test_gallery.py`（新建 10 个用例，全不触网）

### 踩到的坑（都已修复）
1. **`sqlite3.Row` 不支持 `.get()`** —— 首版 get_mirrors 用了 `res.get("mirrors")`，
   导致 56 张图全部下载失败（日志满屏 `'sqlite3.Row' object has no attribute 'get'`）。
   这个错误只在真实跑起来时才暴露，纯单测发现不了
2. **越界 URL 是 200+html** —— 若不加 `require_image` 校验，会把 HTML 错误页
   当图片存下来，且因"下载成功"永不触发镜像切换
3. **探测间隔不能沿用下载间隔** —— 否则光枚举 56 张就要 3~9 分钟。
   拆出独立的 `probe_interval`

- 枚举实测：56 张，边界自动停止正确（00057 起连续 3 次缺失）

## 优化评审：图片与视频链路（仅建议，尚未实施代码）

用户问「还有什么优化建议」。复核现有实现时纠正了两处此前的错误认知。

### 纠正 1：限速器并发结论（上轮说反了）
离线实验（并发孔 3 / 间隔 0.5s / 每次耗时 2s / 6 个请求）：
发起间隔恒为 0.534/0.527/0.939/0.535/0.527s，总耗时 5.07s（纯串行需 12s，证明确实并发）。
→ **间隔闸门全局串行，并发数不会摊薄间隔**。上轮「concurrency 必须为 1」是错的，
且该错误恰好掩盖了视频链路的真问题。
已改 `config.yaml`：`domain_concurrency: 1 → 3`，注释重写为「两个正交闸门」。

### 纠正 2：本机没有 ffmpeg
`shutil.which("ffmpeg")` → None → **m3u8 全部走 `_manual_merge` 降级路径**，
不是备用方案。该路径的缺陷当前全部在生效。

### 视频链路待修（按优先级）
- P0 分片限速：`_manual_merge` 每分片过 `domain_slot`，套用图片的 3~10s 节奏
  → 100 分片 ≈ 11 分钟。分片是同一视频的连续片段，应走独立快间隔（0.2~0.3s）
- P0 分片并发 + 分片级重试 + 断点续传：现在串行、无重试、任一分片失败整个视频报废
- P0 输出 `.ts` 而非 `.mp4`（无 ffmpeg 无解，可评估 imageio-ffmpeg 自带静态二进制）
- P1 分片 `r.content` 整段读内存，应流式写
- P1 视频未走 `download_with_mirrors`（与 image 不一致）
- P1 ffmpeg 失败被 `except Exception: pass` 静默吞掉，stderr 丢失
- P1 无 Content-Type 校验（图片有 `require_image`，视频无对应物）；
  m3u8 判定仅 `".m3u8" in url`，不识别 `.mpd`(DASH)
- P2 加密 m3u8 直接抛错（AES-128 可纯 Python 解，不必 ffmpeg）
- P2 master playlist 已解析 BANDWIDTH 但只选最高，无清晰度选择

### 图片链路待优化
- P0 画质偏好：现在 `.jpg` 原图作主 URL，webp 尺寸变体只当降级备用。
  实测原图 656KB，1200 宽 webp 通常 80~150KB → 应让用户选画质档，省约 80% 空间
- P0 抽公共基类：`gallery.py` 硬编码 `IMG_BASE`/`VARIANTS`，接第二个图集站要复制整份文件，
  与「通用平台」定位冲突
- P1 探测并发：56 张 × 0.3s = 17s，探测是轻量请求，可并发 4 左右
- P1 `.part` 临时文件：现在直接写目标路径，中断留半成品；resume 还可能拼接到 HTML 错误页
- P1 magic bytes 校验：只信 Content-Type 不够（实测是手工看 `\xff\xd8\xff` 才确认的）
- P2 增量采集（缓存相册总数）、pHash 近似去重、图片尺寸过滤（需 Pillow）

### 通用

### 本轮新发现的 bug（已修 + 加回归测试）
**`delete()` 提前 pop `_active` 导致 worker 不退出**
- 原实现：`delete()` → `cancel()` 置取消标志 → 无条件 `pop(_active)`
- 但 `_cancelled()` 是查 `_active` 的，pop 之后读不到标志 → 运行中的 worker
  继续把剩余资源全下完才释放线程池槽位（实测占住约 6 分钟）
- 现象：删掉运行中任务后，新建任务一直 `pending` 排队
- 修复：只在 `future.cancel()` 返回 True（**worker 尚未启动**）时才手动回收条目，
  否则交给 `_run` 的 `finally`
- 验证：修复后删除运行中任务，**2 秒**内新任务即进入 `extracting`
- 回归测试：`tests/test_watchdog.py` 新增 2 个（`_RunningFuture` / `_QueuedFuture`）
- **这个 bug 是上一轮我自己用 DELETE 清理测试任务时触发的**，纯单测发现不了
