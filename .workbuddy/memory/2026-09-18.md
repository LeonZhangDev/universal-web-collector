## ffmpeg 接入: 定位策略 + 双引擎（承接「ffmpeg 安装好了」）

### 暴露的问题
用户已用 winget 装好 ffmpeg 9.0.1-full_build
(`%LOCALAPPDATA%\Microsoft\WinGet\Links\ffmpeg.exe`)，但
`shutil.which("ffmpeg")` **仍返回 None** —— PATH 是进程启动时的快照，
已运行的后端进程读不到新写入的注册表 PATH。

这同时意味着 V14 那批「有 ffmpeg 就优先用它」的分支**从未真正执行过**。

### 改动
1. **新增 `backend/core/ffmpeg.py`**：`find_ffmpeg()` 按序探测
   显式配置(`ffmpeg_path` / `UWC_FFMPEG`) → PATH → 已知安装位置
   (winget Links / scoop shims / choco bin / `C:\ffmpeg\bin` / 商店)
   → `imageio_ffmpeg`。成功永久缓存；**失败只缓存 30s**，
   故装好无需重启后端即可被发现。配置了但无效的路径不报错，继续往下探测。
2. **`config.py`**：新增 `ffmpeg_path`（相对路径按项目根解析）+ `video_engine`，
   支持 `UWC_FFMPEG` / `UWC_VIDEO_ENGINE` 环境变量。
3. **`video.py`**：全面改用 `find_ffmpeg()`，subprocess 走绝对路径；
   新增三态引擎 `auto` / `ffmpeg` / `builtin`；`-nostats` 抑制进度输出；
   `_ffmpeg_merge` 更名 `_ffmpeg_pull`（原名"合并"有误导性，它做的是拉流）。
4. **`scripts/verify_hls.py` 重写**：旧脚本用假分片（`bytes([i+1]) * n`），
   装上 ffmpeg 后 `auto` 会先走 ffmpeg 拉流，而假分片不是合法 TS
   → **脚本直接失效**。改为用 ffmpeg 现场生成真实 HLS
   (testsrc + sine, libx264 + aac, 关键帧对齐分片边界)，
   并加解码级校验（`-f null -` 完整解一遍）与字节级校验
   （按 m3u8 顺序拼接的 sha256，能抓错序/丢块）。
5. **`scripts/start.py`**：新增 `[5/5] 视频引擎 (ffmpeg)` 自检。
   必须用 `find_ffmpeg()` 而非 `which()`，否则会**误报"未安装"**。

### 验证
- `scripts/verify_hls.py`：**18 项断言全通过**（7 个场景）
  - ffmpeg 引擎 → `.mp4`，完整解码通过，时长 6.037s
  - builtin → 内置器分片 + remux → `.mp4`，完整解码通过
  - builtin 无 ffmpeg → `.ts`，**sha256 与原始分片拼接完全一致**
  - auto 无 ffmpeg → 正确降级；ffmpeg 引擎无二进制 → 正确报错、未静默降级
  - 并发 4 = 3.19s vs 并发 1 = 4.26s；缺片恢复后**只请求 `/seg5.ts`**
- 测试：**78 个用例**通过（59 → 78，新增 `tests/test_ffmpeg.py` 19 个）

### 设计取舍
- `builtin` 只约束**下载**方式，不阻止后续 remux —— 用户装 ffmpeg 是为了拿
  通用容器，没必要因强制内置下载而退回 `.ts`
- ffmpeg 拉流时请求由 ffmpeg 自己发出：`DomainLimiter` 不参与、mirrors 不轮换、
  分片进度只在整文件完成时上报一次。这是 `builtin` 存在的另一个理由
  （限速/镜像敏感站点）

### 遗留
- 未在真实视频站点验证 ffmpeg 拉流（本地 HLS 已覆盖协议与请求头逻辑，
  但真实站点的 AES-128 加密流仍未实测）
- 此前列的 P1/P2 项仍在：探测并发、`.part` 临时文件、magic bytes 校验、
  带宽限速、pHash 近似去重、视频未走 `download_with_mirrors`
- git 结构问题（仓库根是整个 `C:\Users\admin`）仍未处理

## 相册页 URL 解析事故 + 删除语义（晚上）

### 事故：输入相册页 URL，任务"成功"但 0 张图
用户给 `https://xchina.co/photo/id-6aa5136f606fe/10.html`，日志是

```
seq 00001 不存在(text/html; charset=utf-8), 连续缺失 1/3 ... extracted 0 resources
no resource to download (all filtered out)   <- 误导：根本没东西被过滤
task success                                  <- 最误导的一句
```

**根因**：`parse_gid` 的 `id_in_path` 只写了 `/photos/(...)`（图片直链形态），
相册页匹配不上 → 走"取路径末段"退路 → 拿到**页码 `10`** 当图集 ID →
去枚举 `photos/10/00001.jpg`。该站对不存在的图集同样返回 `200 text/html`，
3 个序号全判"不存在"，枚举立即停止。

对照实测（HEAD + `Accept: image/*`）：
```
photos/10/00001.jpg            -> 200 text/html; charset=UTF-8
photos/6aa5136f606fe/00001.jpg -> 200 image/jpeg  382383B
photos/6aa5136f606fe/00142.jpg -> 200 image/jpeg   <- 最后一张
photos/6aa5136f606fe/00143.jpg -> 200 text/html    <- 越界
```
密集扫 1..200 确认 **1~142 连续无空洞**，143 起全缺失 → `miss_stop=3` 在这个站安全。

### 修法（三层，都是"宁可报错不猜"）
1. `GallerySite.id_patterns`：多形态正则按序尝试（直链 / 相册页 / query）
2. `page_tail=r"^\d+$"`：末段是纯数字 → 认定页码，**放弃解析**
3. 退路只在末段形如 `[0-9A-Za-z_-]{6,}` 时才兜底；`_run` 里空列表即 `raise`
   → 任务判 `failed` 并给出可读原因

### 顺手抓出的两个 bug
- **文件名双后缀 `00001_.jpg.jpg`**：判断"是否最高画质档"时拿**变体后缀**(`".jpg"`)
  和**画质档名**(`"original"`)比，永不相等 → 原图也被贴标记。
  抽出 `_quality_tag(site, variant)`。
- **看门狗误杀别的实例的任务**：`_watchdog_pass` 只看自己 `self._active`，
  只要进程里有第二个 TaskManager（测试、诊断脚本），单例的看门狗就会把它在跑的
  任务判成"服务重启遗留"标 failed。修：模块级 `_LIVE_MANAGERS` 登记所有存活实例，
  判断前问一遍。⚠️ 仍不覆盖多进程部署（需 tasks.worker_id）。
  **这个坑是我自己的验证脚本先踩到的**——先看到 `task failed: stale task`，差点当成
  下载 bug 去查。

### 删除语义（用户问"删除任务包括删除图片吗"）
答：**不包括**。原 `DELETE /tasks/{id}` 只删记录。现在：
- `DELETE /tasks/{id}` 默认只删记录（去重下别的任务可能引用这些文件）；
  `?with_files=true` 才连 `<下载根目录>/<task_id>/` 一起删，双重越界校验
- `POST /tasks/bulk-delete` 一键清理已结束任务（运行中的不动）
- `GET /tasks/storage` 占用概览（前端"清理已结束 (N)"按钮预检）
- 前端删除改成弹层：**只删记录 / 连文件一起删**两个按钮，不再用 confirm 的三态

### 验证
- pytest **149 用例**（新增 `tests/test_delete.py` 11 项 + gallery 新增 11 项）
- `verify_output.py` 33 项断言仍全过；前端 vite build 72 modules
- 真实站点端到端（单例 `tm.task_manager`，枚举上限压到 3~5 张控制时长）：
  `success` / 全 done / 魔数 `ffd8ffe0` 真 JPEG / original 落 `00001.jpg`(382KB)、
  `quality=1200` 落 `00001_1200.webp`(28KB)
- ⚠️ 验证脚本里 `gb.DEFAULT_MAX = 3` **不生效**：`discover(..., max_count=DEFAULT_MAX)`
  的默认值在 def 时就绑定了，改模块全局没用。要限流得显式传参或包一层采集器。

## V17 视频相册枚举 + 相册标题命名（深夜）

用户：视频也能从相册页 URL / 相册 ID 反推到 `00001.mp4`~`00004.mp4`，
文件名想用网页 `<title>` 的文字。

### 站点实测
```
photos/6a3654854fd25/00001.jpg -> 200 image/jpeg      <- 图片也有
photos/6a3654854fd25/00001.mp4 -> 206 video/mp4  64MB
... 00002.mp4 77MB / 00003.mp4 5MB / 00004.mp4 105MB
photos/6a3654854fd25/00005.mp4 -> 200 text/html       <- 越界
```
**12 张图 + 4 段视频，序号空间相同、靠扩展名区分**。只采图片漏 260MB 视频，
只采视频漏整套图。⚠️ 别反推成"有视频就没有图片"。
`.mp4` 对**任何 Accept（含不带头）都返回 206** —— Accept 在视频路径上不是门槛。

### 改动
- `GallerySite` 增 `video_variants/video_quality_map/video_base`，
  新增 `MediaType`（自带 `ctype_prefix`：图片看 `image/`、视频看 `video/`）
- `options.media`：`auto`(默认) / `image` / `video` / `both`；
  auto 的判定**两条线索都问**：相册页 `var videos` 非空 → 有视频；
  否则探一次 `00001.mp4`。两个都说没有才算没有（页面结构会变，不可只信它）
- 新增 `collectors/album_meta.py`：headless Chromium 读相册页 →
  `<title>`（按 `" - "` 截第一段作目录名）+ `var videos` + `objId` 校验
- `options.album_title`：`clean`(默认) / `full` / `id`。**`id` = 完全不开浏览器**
  （改前代码无条件抓页面，与文档不符，已修）
- 目录名优先级不变：任务级 `name_template` > 采集器建议 > 全局默认；
  采集器建议文件名 `相册名/00001.jpg` 同样过 `safe_relative` 清洗
- `core/naming.py` 导出 `clean_segment()`（标题里的 `/` `:` `?` 必须先清洗，
  否则多一层目录或非法路径）

### ⚠️ 相册页的三个坑（都实测踩过）
1. **首次拿到的是 Cloudflare 挑战页**（`<title>Just a moment...</title>`），
   几秒后自动跳真实页。固定 sleep 不可靠 → 必须轮询。
2. **不能用 `wait_for_function` 等挑战解开**：挑战成功靠**一次导航**完成，
   导航销毁执行上下文，Promise 永远不 resolve（25s 超时也拿不到）。
   而且 8s 时标题是 `Loading <url>`（导航中占位），按标题判定会误判"已就绪"，
   紧接着 `page.content()` 直接抛异常 → **只能轮询 `page.content()` 本身**，
   判定依据是正文里有没有相册页标记（`photo-items` / `hero-title-item` /
   `var videos` / `objId`）。
3. **不要默认带已保存的登录态**：本机 `browser_state/xchina.co.json` 里的
   `cf_clearance` 已与当前 IP 不匹配，带上它 Cloudflare 直接回
   `Attention Required!`（永久拒绝）；**同一时刻匿名反而能过**。
   所以顺序是"先匿名，不合格再带登录态重试"，与 `collectors/browser.py` 相反。
   A/B 实测：带登录态 → 标题永远是 Just a moment；匿名 → 拿到真实标题。

### 顺手修掉的三个既有问题
1. **`tests/test_gallery.py` 有重复定义的用例**：`test_filename_*` 三个函数
   完整粘贴了两遍，**后定义覆盖前定义** → 3 个用例名存实亡（一个都没跑）。
   这是上一轮并行 Edit 静默丢改动的后果。已删重复块并 grep 核对。
2. **`TaskManager.shutdown()` 不等 worker 退出** → 测试里那个 sleep 2s 的慢
   worker 会在**下一个用例**里继续写库（DB 连接是模块级、被 monkeypatch 换过），
   把 `AttributeError` 写进下一个用例的任务，表现为"看门狗用例随机失败"。
   新增 `shutdown(wait=True)`，测试 fixture 使用；生产默认仍 `wait=False`。
3. **`album_title=id` 仍在开浏览器**（见上）。
