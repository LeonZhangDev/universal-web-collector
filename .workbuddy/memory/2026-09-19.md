## V19 采集器自动识别 + Cloudflare 长期对策（已完成并验证）

用户不再需要手选采集器；顺便把 CF 的应对写成长期策略而不是临时 hack。

### 自动识别
- `collectors/scores.py`（新）：分数阶梯单独成模块，**打破循环依赖**
  （`collectors/__init__` 末尾要 import 所有 spider，spider 又要读常量）。
  `ALBUM_PAGE(100) > RESOURCE_URL(50) > BARE_ID(10) > GENERIC(-1000)`。
- `SequenceGallerySpider.match_score` / `GenericSpider.match_score`；`XChinaSpider` 不参与
  （图集 URL 一律归 xchina_gallery，避免并列）。
- API：`POST/GET` 三条链路（create / preview / watch）统一走 `_pick_collector()`；
  新增 `GET /collectors/resolve`（纯 CPU，供界面回显）。库里存**解析后真名**。
- 前端：下拉首项「自动识别」，失焦 300ms 后回显"已识别为 X"，认不出来/不唯一按颜色提示。

**测试先写才抓到的 bug**：第一版只要求"域名 + parse_gid"，`/tag/some-tag` 的末段被
`parse_gid` 的末段退路当成图集 ID 认领 → 会去枚举不存在的图集（又是"成功但 0 资源"）。
修：新增 `parse_gid(strict=True)`，**跳过末段退路**，只认正则配出来的 ID；真实采集仍保留退路。
教训：**替用户做决定的场合一律用最严的那条规则。**

### Cloudflare 长期对策（`collectors/album_meta.py`）
- 立场写进模块文档：**不投入指纹对抗**；真正对策是让采集不依赖那个 HTML 页
  （资源发现走纯 HTTP 枚举，页面只提供目录名/数量/体积），拿不到就降级用 gid。
- 域级熔断：连续 3 次读不到 → 该域 10 分钟不再开 Chromium（每次读页几十秒）。
- 陈旧登录态隔离：带登录态被 `Attention Required!` 拒 → 标记失效；`/sessions` 返回 `cf_stale`。
- 降级可见：所有降级路径写人话并回答"接下来会怎样"。
- 两个易搞反的点：**匿名被拦 ≠ 登录态失效**；**页面结构不符不计入熔断**（那是另一个问题）。
- 测试里的小修正：`loader.html = ""`（连正文都没拿到）原先不计入拦截 → 改成 `not html`。

## V20 XChina 视频页(签名 m3u8) + 前端低成美化（已完成并验证）
- `collectors/hls.py`（新）：`inspect_playlist()` 播放列表健全性校验（expires 过期/分片空指向
  placeholder/密钥不可达三道关）+ 下钻 master；`estimate_size()` 用「单片体积×分片数」估整段。
- 实测抓到最阴险 failure mode：签名过期/错误时站点返回 200+语法合法 m3u8 指向
  `/fallback/placeholder.ts`（603KB 可播放 TS）→ 直接 ffmpeg 会"成功"下成占位视频且报 success。
- `xchina_video` 采集器（新+@register）：/video/ 路径=100、m3u8 直链=50；监听播放器网络响应
  捕获 .m3u8（用 `"m3u8" in u` 而非 endswith，真实 URL 带 ?expires 查询串）；browser_runner 可注入。
- 前端：视频采集器中文名/占位提示/预览面板；补 @media 响应式 + :focus-visible + 暗色滚动条。
- 验证：pytest 266 用例（新增 test_hls_guard 12 + test_xchina_video 9）；端到端 ffmpeg 解出

## 扩展方向调研（网页+论坛，2026-09-19）
用户问 xchina 还有哪些功能可扩展。社区与成熟工具(gallery-dl / 各类批量下载器)的高频需求映射到本项目：
- ① 聚合页采集器（模特/系列/标签/搜索）→ 自然对应"新 collector 枚举 album URL + 委派现有图集采集器"；
  含 list-only / cascade 两种模式 + 分页 lazy-load（需真实站点验 xchina 聚合页 URL 结构与 CF 行为）。
- ② 聚合页级增量：在"per-resource 增量"之上增"重扫模特页、跳过已完整下载的相册"。
- ③ 代理支持（per-task/site）：PicGo/gallery-dl 均强调；项目目前缺。
- ④ HLS 加固：多密钥轮换 + ffmpeg -reconnect 应对抖动 + 相对密钥 URI 解析（hls.py 现假设单密钥）。
- ⑤ 尺寸(宽高)/长宽比过滤 + 感知去重（近重复图片）。
- ⑥ 元数据 sidecar JSON（tags/maker/date/resolution，album_meta 已有数据）。
- ⑦ 429 退避/指数重试/队列优先级/并发上限（项目 ThreadPoolExecutor 固定 2，缺 per-batch 队列）。
所有采集器侧扩展需遵循"先 probe 再信任、失败响亮、不依赖被保护 HTML 页"的既有铁律。

## V21 任务列表增强（已完成，待提交前验证）
用户要求实施"全部建议"：任务名、打包按钮统一、暂停/继续、重试抖动、有效资源定义、自动识别护栏等。

### 落地的改动
- **任务名用相册名**：`tasks` 表加 `name` 列（迁移兼容）；`_run` 提取后由 `_infer_name()`
  从首个资源 filename 首段（图集目录名）或视频 stem 推断回写；schema/前端列表/详情展示。
- **打包下载按钮统一**（`TaskDetail.vue`）：从裸 `<a href>` 改成带 `archiving` loading 态的统一按钮，
  与其他操作交互一致（无 loading 的裸链接是真实 UI 不一致 bug）。
- **暂停/继续**（后端状态机）：新增 `TaskStatus.PAUSED` + TRANSITIONS；`pause()` 置取消标志让
  worker 在资源边界退出并落 paused；`resume()` 把 downloading/skipped/failed 复位 pending、
  **不复用采集、不重下已 done 文件**（相对 cancel+retry 的核心价值）；新增
  `POST /tasks/{id}/pause`、`/resume` 与前端列表行+详情按钮（api.js 加 pauseTask/resumeTask）。
- **重试抖动**：`downloaders/base.py` 指数退避 ×0.6~1.4 随机因子，避免并发失败集体重试风暴。
- **有效资源定义**（`core/filters.py`）：`match_resource()` 统一为 URL/类型+大小+图片下限的单一入口；
  新增 `min_image_bytes`（治 1x1 跟踪像素/广告占位图）；**关键 bug 修复**：`match_size` 接收字符串
  size 会 str<int 抛 TypeError 把整任务拖垮 → 新增 `_coerce_size()` 统一转 int（经 JSON/DB 往返的
  size 是字符串）。两处调用点(提取预筛/下载复核)都走它。
- **自动识别护栏**：`/tag/some-tag` 末段误认领的教训写进 V19 已修；本次未动识别逻辑，靠现有 strict 规则兜住。
