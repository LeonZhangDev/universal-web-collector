# 2026-09-20

## 性能画像分析：下载「慢」的真实构成（未改代码，仅测算）

用户问"下载速度优化 + 上面踩坑的优化还有什么建议"。按实际代码逐段测算，
结论是**下载慢 95% 不是带宽问题，是节奏问题**。以 300 张图、默认配置为例：

| 环节 | 开销 | 来源 |
|---|---|---|
| 枚举探测（串行 sleep） | ~90s | `gallery_base._pause` → 301 次 × `probe_interval=0.3` |
| 下载节奏闸门 | ~150s | `ratelimit.DomainLimiter` 吞吐上限 = 1/min_interval = 2 req/s |
| dHash 子进程 | ~24s | `phash.dhash` 每图 spawn 一次 ffmpeg（默认开） |
| 实际传输 | ~15s | 150MB @ 10MB/s |

**约 280s 开销 vs 15s 传输。**

### ⚠️ 最重要的发现：`domain_concurrency` 在 `min_interval>0` 时几乎不起作用

`ratelimit.py::DomainLimiter.slot()`：每个线程在 `_ilock` 内按 `_last + gap` 计算延迟并
`sleep`，`yield` 才在锁外。所以**请求起点间隔恒 ≥ gap**，站点吞吐硬顶 `1/min_interval req/s`，
与并发数无关 —— 并发只决定同时在飞的请求数，不决定吞吐。
→ **用户"把并发调到 16 还是这么慢"的困惑根源在此。** 唯一有效的是降 interval。

### 其余定位到的点（均为"可改一行/小改动"级）

1. `filters.py:438` 体积探测用裸 `requests.head()`，**不走共享 `SESSION`** → 每资源一次
   TCP+TLS 握手。改 `SESSION.head(...)` 即可复用连接池。（调用点 `task_manager.py:844`）
2. 枚举是纯串行 + 逐个 sleep。可改为**指数探测上界 + 二分定位末尾**（O(N) → O(log N)），
   或探测并发化（HEAD 是轻请求，用站点级节奏而非逐个 sleep）。量级收益。
3. dHash 每图一个 ffmpeg 子进程且**默认开**。可：sha256 已判字节重复的跳过；
   或挪出下载关键路径、下载完成后批量算。
4. `SESSION` 未挂 `HTTPAdapter` → urllib3 默认 `pool_maxsize=10`，跨站点会互相挤占。
5. `CHUNK = 64KB` 偏小，改 256KB~1MB 纯收益。
6. `_download_all` 一次性 submit 全部 future（300 个挂池里），pause/cancel 要 drain；
   可分批提交（如 2×workers）。

### 状态语义不一致（踩坑面）

- **限速器/冷却是进程内的**（`_limiters` / `_COOLDOWN` 模块级 dict），**CDN 画像却落盘**。
  多实例/重启后冷却丢失而画像保留 —— 两类状态一个持久化一个不持久化，语义不一致。
  要么冷却也落库（带过期时间），要么文档写清"冷却仅进程内"。
- 感知去重**只在任务内**比对，而用户真正想要的是跨相册查重（同图出现在多个相册）。
  现状做不到；若要支持需把 dHash 存库并提供只读查询（仍只标记不删除）。
- `check_site` 目前只覆盖 `id_patterns` + `gid_shape`，未纳入 `seq_format` /
  `base_candidate_digits`。

## 检索外部方案后的修正（比原建议更好的两处）

### A. 令牌桶：当前实现是「容量=1 的退化桶」，有精确解释
业界共识是**用令牌桶替代逐个 sleep**。关键一句（mikenguyen13 / proxiesapi 指南）：
「b=1 时退化为严格每 1/r 秒一个请求；b 更大则容忍短簇」。
→ 现状 `DomainLimiter` 正是 **b=1**：锁内按 `_last+gap` 排队，长程平均速率被
  限死的同时**连一点突发都不允许**。修法不是降 interval，而是**保持平均速率、
  放开突发容量**（rate=1/min_interval, capacity≈并发数）。礼貌性不变，串行惩罚消失。
  这比我上一轮"降 interval"更优 —— 降 interval 是拿礼貌性换速度。

### B. 自适应节流：Scrapy AutoThrottle 是现成参照，但**不能照抄**
算法：`target_delay = latency / N`；`new_delay = (old + target)/2`；
**非 200 响应不允许降低 delay**（错误响应通常比正常响应快，否则会越错越快）。
⚠️ 但它是**纯延迟驱动、不看状态码**，在两种场景下反而是帮倒忙（dev.to 分析）：
  ① CDN 边缘缓存亚毫秒返回 → 判定"服务器很闲"→ 疯狂加速；
  ② 429 也能毫秒级返回 → 同样被当成健康。
本项目两个条件**都命中**（img.xchina.io 是 CDN、站点会快速 429）。
→ 正确做法 **AIMD + 状态码优先**：加性增（连续成功缓慢收紧间隔）+ 乘性减
  （429/403 立即冷却，已有），延迟只做**次级**调节量；非 200 绝不触发增速。

### C. ⚠️ 发现一个缺口：冷却是单向阀，间隔永不恢复
现有 cooldown 到期后 `domain_min_interval` 回到配置值，**没有"加性增"**。
站点一旦被限过一次，后续只能靠人工改配置才提速。B 的 AIMD 正好补上这一半。

### D. 枚举：比二分更好的一级 —— 用页面自报数量直接跳过上界搜索
`album_meta.extract_album_meta()` 已经返回 `photos`/`videos_declared`（站点自报数）
和 `resource_urls`（页面直链，限 60 条，目前**只当 CDN 基址线索用**）。
所以最优是三级阶梯，而不是直接上二分：
  L0 有自报数量 → 直接取 N，只验首尾几个（**探测数 ≈ 常数**）
  L1 无自报数   → 指数探上界 + 二分定位（O(log N)）
  L2 兜底       → 线性扫描（现状，O(N)）

### E. 连接池（外部佐证，比我原判断更具体）
- `pool_maxsize` 默认 10 要**按并发数设**；否则 urllib3 开多余连接再丢弃，
  打 "Connection pool is full, discarding connection"，池化收益白丢。
- 应显式 `pool_block=True`：让线程等空闲连接，而不是反复建连丢弃。
- `timeout` 建议拆成 `(connect, read)` 元组（业界常用 `(10, 60)`）。
  现状 `request_timeout=30` 单值同时作用于 connect 与 read，大文件的读超时偏紧。
- 裸 `requests.head()` 每次新建连接 = 每次 TCP+TLS 握手（与我上一轮定位一致）。

### F. 明确**不建议**做的
单文件多线程 Range 分片下载（aria2/axel 式）：对图集站是明显异常流量特征，
易触发封禁，且本项目瓶颈根本不在传输带宽（传输只占 5%）。收益/风险比不划算。

## V26 实施：下载速度优化（全部建议落地）

### 1. ⚠️ 最重要的诊断：吞吐由**间隔**决定，不由并发决定
旧实现每请求前持锁按 `_last+gap` 排队 = **容量 1 的退化令牌桶**：长程速率被限死
的同时连一点突发都不允许。所以「并发调到 16 还是这么慢」是必然。
修法不是降 interval（拿礼貌性换速度），而是放大桶容量 —— 平均速率不变，只是允许
把攒下来的配额一次花掉。`domain_burst=3`。
另加 AIMD 补上「只减不增」的缺口：连续 8 次成功收紧一档（地板 `domain_fast_interval`），
失败/429 立即翻倍放宽（天花板 `domain_slow_interval`）并清零计数。
⚠️ **不看响应延迟**（Scrapy AutoThrottle 那套在本项目帮倒忙）：CDN 边缘缓存与 429
都毫秒级返回，会被当成"服务器很闲"。只按成功与否判定。
⚠️ 只有传输层/服务端失败才计入放宽；Content-Type 不合是这条 URL 的问题。

### 2. 枚举快路径（真站实测 117→6 次探测，61.7s→2.6s，资源数 114 完全一致）
L0 页面自报数量 → 抽样校验后跳过逐张探测；L1 指数+二分（**默认关**）；L2 线性兜底。
⚠️ L1 默认关是刻意的：二分假定序号连续，中间缺一张就把上界定在缺口之前 =
「300 张只采到 4 张」的**静默截断**，比慢更糟。
⚠️ 抽样点**必须含首尾**（数量错一个 / 起点错一位是最常见的两种不一致）。
任一不中即退回逐张扫描 —— 最坏只是多花几次探测，不会采错。

### 3. 连接池与传输
- `HTTPAdapter(pool_maxsize=max(10,并发×2), pool_block=True)`：默认池满时"建了又丢"
- ⚠️ `pool_block=True` 的前提是**响应必须关闭**：416/429/内容校验这些提前退出路径
  都没读响应体，连接不归还 → 泄漏到池满就是**永久阻塞**（卡死而非报错）。
  已用 `try/finally: resp.close()` 兜住
- `probe_size` 改用共享 `SESSION.head`（裸 requests.head 每次新建连接 = 每次握手）
- `CHUNK` 64KB→256KB；超时拆 `(connect 10, read 120)` 元组

### 4. 降开销与可观测
- sha256 命中**别的任务**时跳过 dHash（感知比对只在任务内，那次解码必然白做）
- `check_site` 纳入 `seq_format` / `base_candidate_digits`（写错就是 0 资源 → failed）
- 任务日志打「站点节奏 …→ 长程约 N req/s」+ 预计耗时（看不见的阈值会被反复误调）

### 5. ⚠️⚠️ 本轮踩到的四个坑
1. **可重入死锁**：`interval`/`rate` 属性各自取锁，而 `_wait_token`/`describe`
   持锁后调用它们 —— 普通 `Lock` 不可重入，**当场死锁**，表现为"调一次就整个进程
   卡住"，堆栈完全看不出。修法：锁内就地计算 + 锁换 `RLock` 兜底。
   （排查时整个 pytest 挂死 120s，只能靠 `timeout` + 重定向到文件定位。）
2. **`sqlite3.Row` 没有 `.get()`**：误用抛 AttributeError，而该位置在 try 里 →
   被当成"下载失败"，测试表现为 `assert 'failed' == 'filtered'`，离真相很远。
3. **`finally` 里的异常覆盖原异常**：给响应加 `close()` 后测试替身没有该方法 →
   AttributeError 在 finally 抛出、掩盖真实原因、重试循环继续 → 最终报成
   "pop from empty list"。**替身要模拟真实对象的完整契约**。
4. **写测试期望前先确认数据形态**：序号 5 位补零，`"/0030.jpg" in url` 永远不匹配，
   "中间缺一张"的场景根本没生效。
