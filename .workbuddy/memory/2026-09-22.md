## CI 首次跑红并修复（用户报「Some checks were not successful」）

### 现象
推送后 GitHub Actions 首次运行（仓库此前无远端，CI 从未跑过）：
`backend` job 失败、`frontend` 通过、`docker` 因 `needs` 被跳过。

### 根因（一句话）
`2492fe3`（当时推上去的提交）的 `pyproject.toml` 里 **`dev=["pytest"]`，没有 `httpx2`**，
主依赖也**没有 `curl-cffi`**。于是 `uv sync --group dev` 装了 26 个包但没有 httpx2，
`starlette.testclient` 导入时直接 `RuntimeError: requires the httpx2 package`，
**5 个测试文件在 collection 阶段就炸**（都 import TestClient）→ exit code 2。

### ⚠️ 最容易被带偏的一点：CI 跑的是 `origin/main`，不是本地 HEAD
本地 `main` 当时已经是 `f389338`（领先远端 **29 个提交**），是一次
`codex/xchina-collector-integration` 分支合并的结果。**修复早就在本地**——
`6960dde [tests] fix: declare TestClient dependency`（补 httpx2）、
`cc94d8d [xchina] fix: impersonate browser TLS for media`（补 curl-cffi）都在那 29 个提交里，
只是从没推上去。排除故障时一度以为"锁文件坏了"，其实是**在拿本地 HEAD 的 `uv.lock`
去解释远端的 CI 日志**。诊断入口应该是 `git log --oneline origin/main..HEAD`。

顺带：本项目仓库有**自动提交机制**会在会话之间提交（HEAD 在会话中途从 `2492fe3` 变成
`f389338`），所以判断"当前状态"前必须先 `git rev-parse HEAD` + `git ls-remote origin`，
别用上一轮的记忆当事实。

### 诊断手法（无 gh CLI 时）
1. `git credential fill` 取 GCM 里的 `gho_` token（`printf "protocol=https\nhost=github.com\n\n" | ...`）。
2. 列运行：`GET /repos/{o}/{r}/actions/runs`；列 job/step：`.../actions/runs/{id}/jobs`。
3. **拿日志**：`GET .../actions/jobs/{job_id}/logs` —— 带 token 时**直接返回纯文本**
   （不是 zip，别按 zip 解）；Git Bash 的 `/tmp` 传给 Windows Python 会找不到，用
   `C:/Users/admin/AppData/Local/Temp/...`。
4. 本地复现 CI 环境：`UV_PROJECT_ENVIRONMENT=<临时目录> uv sync --group dev`，
   对比 `uv export --group dev --no-emit-project` 解析出的包数 vs CI 日志里的
   `Installed N packages`。本例 local 33 / CI 26，差值恰好是缺失的两棵依赖树。
5. 用这个干净环境跑一遍 pytest（无 Playwright 浏览器、有 httpx2）——最接近 CI 的条件。

### 修复
无需改 CI：把本地 `main` 推上去即可。`git push origin main`（`2492fe3..f389338`，29 个提交，
含那两处依赖声明 + uv.lock 重生成）。新 run `35717962425` → **backend / frontend / docker 三绿**，
耗时 95s。

### 结论
CI 这次红**不是误报**，它准确指出了"被推上去的那个提交依赖声明不完整"——正是 CI 该干的事。
不要为了"让它绿"去改 workflow；`--locked` 也救不了这种情况（pyproject 与 lock 当时是自洽的，
只是两者都缺依赖）。

## 下载层"深度"审计（用户提出"想要功能深，不只是广"）

通读 `downloaders/` + `core/task_manager.py` 后的结论：**传输正确性那一层已经很深**
（原子落盘 + `.part.src` 来源绑定、Range 续传 + 416 判定、长度校验且遇 Content-Encoding 跳过、
Content-Type 白黑名单、mirrors 切换并跟随扩展名、429 站点级冷却、AIMD 只看成败不看延迟、
代理熔断、`x` 独占新建防两份字节交错、ENOSPC 分类 + abort 广播、HLS master 下钻 + 时长校验 +
分片级续传）。**不要再往这层加东西。**

### 三个已核实的真实缺陷（都不是"新功能"）

1. **永久失败与暂时失败不分** —— `base.py:558` `if isinstance(e, requests.RequestException):
   note_failure(url)`。`raise_for_status()` 抛的 HTTPError 是 RequestException 子类，所以
   **403/404/410 也会触发站点级 AIMD 减速**。一张已删除的图会让整个站点后续都变慢；且每张
   404 都要走满 3 次退避重试（~20s/资源）。
2. **直链媒体无内容校验** —— `_download_file`（video.py:227）只传 `reject_ct=REJECT_CT`（挡 HTML），
   不调 `_probe_media_duration`；该函数只在 HLS 路径用（video.py:313）。长度对但内容截断的 mp4
   会被判成功。图片同理：`task_manager.py:1342` 只调 `image_dimensions`（仅解析文件头）。
3. **"坏文件"信号被静默丢弃** —— `core/phash.py:decode_gray` 解码失败返回 None → dhash 返回 None
   → 只是"不标记重复"，**没有任何地方记录"这张图解不开"**。这是零成本就能拿到的坏文件检测信号。

### 其他缺口（纵深类，非缺陷）
- 无缩略图：`LibraryPanel.vue:164` 用 `/files/raw` 直接铺**原图**（object-fit: cover），大图列表会卡。
- 无资源级遥测：resources 表无耗时/重试次数/失败分类/etag/resolved_mirror 字段。
- 增量只按 URL 匹配（`find_done_resource`），无 ETag/If-None-Match → 同一 URL 内容被替换发现不了。
- 无字节带宽上限（只有 req/s）；无下载优先级（futures 一次性全提交）。
- 无 EXIF、无视频元数据落库；无后处理（转码/打包/巡检）。

优先级建议：P0 = 1/2/3（缺陷），P1 = 资源遥测 + 缩略图 + 条件请求 + 带宽，P2 = 后处理/巡检/死信重放。

## V33 · 下载层深度（用户选「P0 三个缺陷」）

用户原话：**「现在我不止想功能广，我想功能比较深」** → 我按四层模型摸底后指出传输正确性
已经很深，缺口在别的层；给出 3 缺陷 + 7 纵深项，用户勾选 P0。

### 三条实现（都是"跑通但结果错"）
1. **4xx 被当成站点限流**（影响面最大）—— `raise_for_status()` 抛的 `HTTPError` 是
   `RequestException` 子类 → 404 走 `note_failure(url)` → **整域名后续请求间隔翻倍**；
   且永久失败还要走满 3 轮指数退避（每张 ~20s）。
   修：`PERMANENT_STATUS = {400,401,402,403,404,405,406,410,451}` 在 `raise_for_status()`
   之前分流成 `GoneError`；重试循环 `except GoneError: raise`（放在 `except Exception` 前）。
   界限：408/429/5xx **不**进这个集合（5xx 的 note_failure 是对的）。
   ⚠️ `download_with_mirrors` 里 GoneError **要继续试下一个镜像**（4xx 是"这份副本没有"）。
   新增资源状态 `gone`：自动不重试、手动可重试；`_final_status` **计入失败**。
2. **直链媒体只校验字节数** —— 两层修：`core/mediacheck.py`（新，算术级，只读头尾 32B，
   RIFF/BMP 长度字段恰好相等 + ISOBMFF box 链不越界 + JPEG EOI/PNG IEND/GIF 0x3B）；
   `video.py::_validate_direct_media`（ffprobe 时长，直链原来完全没这层）。
   **不做"解码一遍"**：慢 + 方向不明（解码器对损坏文件宽容，对冷门封装误判）。
   四条"宁可漏报不可误报"约束见 GUIDE §12.2。
3. **解码失败被静默丢弃** —— `phash.decode_gray_ex` 拆成 `NO_DECODER`（缺 ffmpeg，放行）
   / `DECODE_FAILED`（ffmpeg 在却解不开 = 最强坏文件证据）。合并这两者就是原实现的
   根本问题。`returncode==0 但吐不满一帧` 也算 DECODE_FAILED。只标记不删。

### 第 9 条静默坑：拿人看的文案当数据用
界面原来用**正则解析 note 字符串**归类失败原因（`/\b403\b|forbidden/`、`/timeout/`）。
措辞一改归类就静默失效、换语言全落"其他"、也没法支持"按原因筛选/批量重试"。
修：`resources.error_kind`（8 个固定取值，由 `errors.classify()` 统一给出）。
⚠️ 三条易错：① `classify` 按**名字**识别 RateLimited/HTTPError（否则与 base.py 循环依赖）；
② `db.error_kinds()` **不能按 status 过滤**（`corrupt` 会落在 `done` 上，恰好漏掉最该看的）；
③ 中文标签由后端下发（`KIND_LABELS`），前端那份只是兼容旧后端的兜底。
⚠️ `gone` 一引入就有**三处口径**必须一致：`_final_status` / `summarize_resources` / 前端
`failedSkippedCount`。`summarize_resources.failed` **包含** gone，另给单独的 gone 字段。

### 环境坑（本轮又踩）
本机 `uwc-verify` 缺 `curl-cffi`（**主依赖**，TLS 指纹必需）→ `test_downloaders.py` 3 项 +

## V33 收尾（同日继续）：两个 fixture 缺陷 + 一个真缺陷

### ① `mediacheck` 的 box 链误报 → 换成类型白名单

用户要的文件。判据从"像不像类型名"收紧成"是不是**认识的**顶层 box 类型"。
⚠️ 试过两版启发式都被骗过（可见 ASCII 正则 → alnum+空格），最后 `_TOP_BOX_TYPES` 白名单才成。
实测：真实 mp4 / +追加注释 / +追加伪 free box → 全 `None`；截断一半、**少 1 字节** → 都报错。

### ② `verify_output.py` 的 mp4 fixture 是假的
它自己的注释写着"下载层只做流式落盘 + Content-Type 校验，不解析容器" —— 这句假设被 V33
推翻了。假 mp4 现在被**正确地**判成坏文件删掉，红的是「视频任务应当成功」。
**根因在 fixture 说谎**。改成内嵌 base64 的真实 mp4（64x64/10fps/1s，1605B）——
Handler 还会往后追加 `<!--文件名-->`，正好钉住①那个边界。回到 40/40。

### ③ `verify_hls.py` 偶发红：素材抖动伪装成下载层缺陷
不写 `-hls_playlist_type vod` 时，ffmpeg 靠"hls_list_size==0 就当 VOD"隐式收敛决定要不要
收尾，**6 次里出现 1 次**产出只列 11 片、无 `#EXT-X-ENDLIST` 的中间态 → 撞上 hls.py 的
完整性门禁 → 报「站点播放列表缺少 ENDLIST」。加 `vod` + **素材自检**（缺 ENDLIST 或
"列出片数 ≠ 磁盘片数"就以**素材**名义 exit 2）。
先 `git worktree add --detach` 跑纯净 HEAD 证明「不是我改坏的」——这一步值得，省下瞎改。
⚠️ 5 次复现不出来时**不要收手**，这类抖动只会让你下一轮再白花半小时。

### ④ 真缺陷：`cdn_profile` 并发写静默丢一半（顺手收掉，也是套件偶发变红的原因）
读者（`preferred_bases`/`summarize`）**不走锁**，写者靠 `tmp.replace(p)` 换文件。
Windows 上目标只要有别的句柄开着（哪怕只读）→ `os.replace` 抛 `PermissionError` →
被 `except OSError: pass` 吞掉。实测「1 个只读线程 + 1 个写线程」：**写 300 次只记下 150 次**。
修：`threading.Lock` → **`RLock`** + 读者进临界区 + `replace` **5 次线性退避重试**。
⚠️ 必须 RLock：`record_hit` 要在同一次"读-改-写"里调 `_read`/`_write`，两者各自也要加锁，
普通 Lock 会**自锁死**。读者侧靠锁，外部占用（编辑器/杀毒）靠重试。修后 300/300。
回归测试**反向确认过**：跑在修复前版本上稳定 `assert 103 == 200`。

### 第 10 条静默坑：`except OSError: pass` 写在一个"本来就会失败"的写入上
等于把**数据丢失**改装成静默。判据两问：失败会发生吗？失败之后有人知道吗？
两个都答"否"的地方，至少要加一次重试，或者留一条可观测痕迹。

### 通用教训：产品加了校验，就要回头问「fixture 还诚实吗」
不诚实的 fixture 会把**产品缺陷和测试缺陷混成同一个红**。本轮有三个 fixture 属于这类
（verify_output 的假 mp4、verify_hls 的未收尾播放列表、以及注释里那句已失效的假设）。

### ⚠️ 行尾陷阱（本机必查，已踩）
`Path.write_text()` 在 Windows 上默认把 `\n` 翻成 `\r\n`。本仓库 `core.autocrlf=false`
且**无 `.gitattributes`**，git 原样存盘 → 用 Python 改写过的文件会**整份变 CRLF**，
diff 从 71 行炸到 415 行（TaskDetail.vue 96 → 1312）。
- 提交前必查。本轮中招：`cdn_profile.py`(LF→CRLF)、`TaskDetail.vue`(LF→CRLF)、
  `test_features_v33.py`(新文件 CRLF)。已用**二进制** `read_bytes().replace(b"\r\n", b"\n")` 修回。
- ⚠️ `backend/downloaders/video.py` 与 `scripts/verify_output.py` 的 **HEAD 本来就是 CRLF**，
  别去"统一"，那会造出反向的巨型 diff。
- 用 Python 改文件时用 `write_text(..., newline="")` 或直接 `write_bytes`。
