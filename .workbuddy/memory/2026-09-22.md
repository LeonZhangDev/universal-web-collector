## CI 首次跑红并修复（用户报「Some checks were not successful」）

### 现象
推送后 GitHub Actions 首次运行（仓库此前无远端，CI 从未跑过）：
`backend` job 失败、`frontend` 通过、`docker` 因 `needs` 被跳过。

### 根因（一句话）
`2492fe3`（当时推上去的提交）的 `pyproject.toml` 里 **`dev=["pytest"]`，没有 `httpx2`**，
主依赖也**没有 `curl-cffi`**。于是 `uv sync --group dev` 装了 26 个包但没有 httpx2，
`starlette.testclient` 导入时直接 `RuntimeError: requires the httpx2 package`，
**5 个测试文件在 collection 阶段就炸**（都 import TestClient）→ exit code 2。

### ⚠️ 最容易被带偏的一点：CI 跑的是 `origin/main`，不是本地 HEAD
本地 `main` 当时已经是 `f389338`（领先远端 **29 个提交**），是一次
`codex/xchina-collector-integration` 分支合并的结果。**修复早就在本地**——
`6960dde [tests] fix: declare TestClient dependency`（补 httpx2）、
`cc94d8d [xchina] fix: impersonate browser TLS for media`（补 curl-cffi）都在那 29 个提交里，
只是从没推上去。排除故障时一度以为"锁文件坏了"，其实是**在拿本地 HEAD 的 `uv.lock`
去解释远端的 CI 日志**。诊断入口应该是 `git log --oneline origin/main..HEAD`。

顺带：本项目仓库有**自动提交机制**会在会话之间提交（HEAD 在会话中途从 `2492fe3` 变成
`f389338`），所以判断"当前状态"前必须先 `git rev-parse HEAD` + `git ls-remote origin`，
别用上一轮的记忆当事实。

### 诊断手法（无 gh CLI 时）
1. `git credential fill` 取 GCM 里的 `gho_` token（`printf "protocol=https\nhost=github.com\n\n" | ...`）。
2. 列运行：`GET /repos/{o}/{r}/actions/runs`；列 job/step：`.../actions/runs/{id}/jobs`。
3. **拿日志**：`GET .../actions/jobs/{job_id}/logs` —— 带 token 时**直接返回纯文本**
   （不是 zip，别按 zip 解）；Git Bash 的 `/tmp` 传给 Windows Python 会找不到，用
   `C:/Users/admin/AppData/Local/Temp/...`。
4. 本地复现 CI 环境：`UV_PROJECT_ENVIRONMENT=<临时目录> uv sync --group dev`，
   对比 `uv export --group dev --no-emit-project` 解析出的包数 vs CI 日志里的
   `Installed N packages`。本例 local 33 / CI 26，差值恰好是缺失的两棵依赖树。
5. 用这个干净环境跑一遍 pytest（无 Playwright 浏览器、有 httpx2）——最接近 CI 的条件。

### 修复
无需改 CI：把本地 `main` 推上去即可。`git push origin main`（`2492fe3..f389338`，29 个提交，
含那两处依赖声明 + uv.lock 重生成）。新 run `35717962425` → **backend / frontend / docker 三绿**，
耗时 95s。

### 结论
CI 这次红**不是误报**，它准确指出了"被推上去的那个提交依赖声明不完整"——正是 CI 该干的事。
不要为了"让它绿"去改 workflow；`--locked` 也救不了这种情况（pyproject 与 lock 当时是自洽的，
只是两者都缺依赖）。
