### 八项与关键设计决定

1. **资源级遥测** `resources` + `started_at`/`finished_at`/`attempts`。
   写入点收拢成 `begin_resource_attempt`/`finish_resource_attempt`（散在各分支迟早漏一处）；
   `resume`/手动重试**清零重算** attempts，否则界面上的"重试 7 次"横跨好几轮。
2. **缩略图 + 修掉从不存在的 `/files/raw`** ← 见下面「两个静默问题」。
   `core/thumbs.py` 缓存到 `_meta/thumb/{sha}.jpg`（**按 sha 不按路径**，同内容只生成一次）。
3. **条件请求 ETag/Last-Modified**。⚠️ 唯一易错点：**有 `Range` 时不能带条件头** ——
   本地已最新时服务器答 304 而非 206，于是"416 = 本地已完整"那条收尾路径永远走不到，
   `.part` 再也收不了尾。让位规则写死在 `_stream_one`。
4. **全局字节速率上限** `max_download_bytes_per_sec` / `UWC_MAX_BPS`，`5MB`/`512k` 写法。
   桶**全局共享**（用户要控的是"程序总共占多少带宽"）。节流点必须**可取消**。
   与 `domain_min_interval` 是两件事：后者管**请求**速率，前者管**字节**速率。
5. **资源库批量** `/library/bulk-delete`（按 `refs` 决定是否真删文件）+
   `/library/archive`（zip 流，不落临时文件）。
6. **完整性巡检** `POST /library/verify`，区分缺失/截断，新增 `error_kind='missing'`。
   **只标记不删** —— 算术判据误报的代价是删掉好文件。
7. **熔断持久化** `core/proxy_health.py`（按代理 URL 分桶，跨任务全局）。
8. **Pexels 集合/搜索页** `/v1/search` + `/v1/collections/{id}`。
   ⚠️ 集合端点形状与搜索页不同，且站点用过两种（`photos` / `media`，后者每项外包
   `{type:"Photo",...}`）。**两种都认**，只认一种会表现成"集合是空的"而不是报错。

### 新增 `core/jsonstore.py`：JSON 状态存储的唯一实现

`cdn_profile`（V33 修过）与新的 `proxy_health` 现在**共用**四条并发纪律：
读写都进 `RLock` + `tmp`+`replace` 原子落盘 + `replace` 退避重试 + 写不进去不假装成功。
**不要为新状态文件手写第二遍** —— 手写一遍 = 少一条纪律 = 又是静默丢一半。

### 两个"看不见"的问题（本轮顺带收掉）

**① 前端资源库引用的 `/files/raw` 这个接口从来不存在。**
图片全是 404，但走 `<img onerror>` 把失败图藏起来 → 界面看起来只是"没有缩略图"，
**不是报错**。静默失败的新变体：请求根本没成功，却没有任何信号。

**② 测试隔离存在"窗口期"。**
`monkeypatch.undo()` 会把 `DB_PATH` 还原成**真实路径**。于是在
「某个用例 teardown 之后 → 下一个用例 setup 之前」这段窗口里，任何 DB 访问都落到
**用户的真库**上。能干这活儿的：看门狗的心跳线程、没 close 的 `TestClient` portal 线程、
别处 fixture 的终结器。

⚠️ **指纹守卫不够**，两个理由：
- 只能**事后**发现"文件变了"，且**同一次变更只能发现一次** —— `_migrate()` 幂等，
  加一列之后真实库永久"正确"，再犯看不出来；
- 报错只有"db 变了"，**没有是谁改的**。

修：`isolation.install_real_db_guard()` 包装 `db.get_conn`，在**打开的那一刻**判
`DB_PATH` 解析后是否等于真实库 → 带调用栈 AssertionError。
两道闸各管一段：即时守卫抓"谁干的"，指纹守卫兜"清单漏登记"。

## ② P1 断点续传持久化（`core/partials.py`，新）

**按 URL 寻址**（不是按路径）：`_meta/partial/{sha1(url)[:2]}/{sha1(url)}.part` + `index.json`。
判据只有一条：**下次同一个 URL 再来，能不能取回**。

| 时机 | 行为 | 理由 |
| --- | --- | --- |
| `TaskCancelled` | **park** | 用户只是不想现在下 |
| `CorruptMediaError` | **删** | 字节已证明是坏的，存起来污染下次 |
| `DiskFullError` | **删** | 快满盘了还留半成品说不通 |
| < `partial_min_bytes`（256KB） | 不 park | 残片重建成本比索引还低 |

TTL 72h + 预算 2GB，按"最久未用"淘汰；`lifespan` 启动扫一次。
`GET/DELETE /library/partials` + 前端概览条 —— **隐性磁盘占用必须可见**，否则
"目录 8GB 而可见产物 6GB"会被当成程序偷偷吃盘。

## ③ P2 标签 / 收藏

独立 `resource_tags` 表（**FK 级联删除**）+ `resources.favorite`。标签大小写归一
（`COLLATE NOCASE` 唯一索引，不在应用层 `lower()` 两遍），单资源 ≤20 个、单标签 ≤24 字。
收藏是**独立维度**，不是"打一个叫 favorite 的标签"（混在一起后按标签筛会多出一堆收藏项）。

## ④ P3 DASH（`downloaders/dash.py`，新）

纯解析（**不碰网络**，便于单测）+ 下载方法，复用既有分片限速/重试/取消/续传。
支持 `SegmentTemplate`（`$Number$`/`$Time$`+`SegmentTimeline`）与 `SegmentList`；
视频取最高档 + 音频单独一轨 → `ffmpeg -c copy` 合并。

三个守住的点：**初始化段必须排在最前**（少了它 = 字节够但播放器判损坏）·
**DRM 必须明确报错**（硬下得到的"成功"文件打不开，比失败更糟）·
**落盘后仍过时长终检**（ffmpeg 退出码 0 但只封前一小段是真实存在的假成功）。

## ⑤ ⚠️ 顺带修掉：分片下载的**连接泄漏**（真缺陷，最值钱的一条）

`_fetch_segments`（HLS/DASH **共用**）在 `raise_for_status()` 失败时**没关响应**。
一条 404 漏一个连接，池只有 8 个 → 漏满后所有 worker 阻塞在 `urllib3._get_conn`，
表现为**整个任务卡死不报错**。

**诊断路径才是教训**：我先猜"测试服务器单线程"→"限速死锁"→"ffmpeg 参数"，全错；
`faulthandler.dump_traceback_later(45, exit=True)` 打了一次调用栈，一眼看到 `_get_conn`。
> **卡死类问题的第一动作是打调用栈，不是猜。**

暴露它的路径也很绕：DASH 素材没生成到清单旁边 → 全量 404 → 连接漏光。
**"素材问题"和"下载器卡死"看起来毫无关系** —— 与 V33 的 fixture 诚实性同源。
