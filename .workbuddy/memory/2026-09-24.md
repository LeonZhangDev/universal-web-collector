# 2026-09-24

## 起因：用户说「你可以自行搜索一些美女相册网站的去测试」

我**没有**去搜集成人/色情相册站（那等于提供色情资源导航）。但这对测探针**没有损失** ——
探针要测的是站点的**技术形态**（序号枚举 + 直链命名 + 存在性判定），与图片内容无关。
所以改用**形态相同、内容合法**的真实站点：

| 靶子 | 形态 | 结果 |
| --- | --- | --- |
| **MangaDex**（官方漫画平台，有公开 API） | `/data/<hash32>/<seq>-<内容sha256>.png` | ✅ 可达，**暴露 2 处缺陷** |
| **Lorem Picsum**（免费图库） | `/id/<n>/<w>/<h>.jpg`，越界 404 | ✅ 可达，**暴露 2 处缺陷** |
| **xkcd** | `/comics/<slug>.png`（非序号） | ✅ 正确判「非序号枚举型」exit 2 |
| **Internet Archive** BookReader | `BookReaderImages.php?zip=…&file=…_0001.jp2` | 末段无媒体扩展名 → 按页面处理，exit 1 |
| 漫画柜 `manhuagui.com` | —— | 连接超时（不可用） |

**方法论的要点**：本地假站点只能验「我**想到**的行为」；真实站点的 URL 形态是
**想不出来**的。两类靶子各有各的用处，谁也替代不了谁 ——
本地假站点当**回归靶子**（结论不漂），真实站点当**找自己 bug 的靶子**（形态超出想象）。

## 五处缺陷：全都不是崩溃，全是「产出错误」

探针跑得通、报告看着像回事，错的是**它给出的结论**。所以「跑得通」发现不了。

| # | 原本会做什么 | 症状 | 修法 |
| --- | --- | --- | --- |
| 1 | 序号后的**高熵内容哈希**被当成「画质后缀」 | MangaDex：草稿写「第 2 页 = `2-<第1页sha256>.png`」→ 必然 404。而它**自己已测出** `命中 1/6`，却照样把草稿打出来 | 新增 `suffix_is_opaque()`（≥40 字符 或 含 ≥16 位连续 hex）→ **拒绝出草稿**，exit 2 |
| 2 | 给 ⑤ 自检**没通过**的 URL 编一个期望 gid | 报告写着 `-> None`，`id_samples` 却配了采信直链的 gid = **编证据**，`check_site()` 拿它空转 | ⑤ 返回逐条解析结果，`id_samples` 只写自检通过的 |
| 3 | 末尾**整段是数字**的路径被当「相册桶号」 | picsum `/id/1040/…` → `base=/id/` + `base_candidate_digits=1040`，基类去展开上千候选 | 数字紧跟在 `/` 后（整段）不当桶号；桶号 > 99 也不认 |
| 4 | 多段 base_path 去数字后留尾随 `/` | 生成 `/id//(\d{4,})/…` —— 匹配不上任何真实 URL，却「看着写好了」 | `rstrip("/")` |
| 5 | 命中 **0** 个序号时照样打印草稿 | 那份声明每一条都是猜的，没有任何实测支持；而人只翻到草稿那一段 | 草稿顶部加强横幅；命中 **1** 个另加**歧义**提示 |

## 第 1 条附带的口径教训：① 与草稿自相矛盾

① 用实测说「只有第 1 个序号存在」，草稿却说「改序号就能枚举」——两句话出自**同一个
程序**，而照抄的那份是错的。修法：命中 1 个 → 明说是**歧义**（①图集只有 1 张
②每页文件名各不相同 ③序号不从 1 开始）+ 给出分辨方法（**再给一条不同序号的直链**）。

> 这条与第 16 条（从一条样本生成规则）同族，但更狠：不只是"规则比样本窄"，
> 而是**同一个程序的另一段已经拿到了反证**，却没被用上。

## 判据为什么取宽

`suffix_is_opaque` 的阈值（≥40 字符 / ≥16 位连续 hex）是**刻意宽松**的：
漏判成"不透明"最多多看一眼、多跑一次；判反了就生成一份「任务 success 但 0 资源」
的声明。**按误报的代价决定判据松紧** —— 这里宁可误报。

### 顺手抓出第 19 条（比上面五条都值钱）

跑全量时 `.full.txt` 出现 **3 个红**，且都在**无关**文件里（`test_incremental` /
`test_pause_resume` 的看门狗用例）。**单跑全绿、连跑才红** → 判定为跨用例污染，不是时序抖动。

**根因**：`backend/core/task_manager.py` 末尾的模块级单例 `task_manager = TaskManager()`
**在 import 期就 start 了**看门狗与调度两个线程，而它们读的是**当前用例的** `DB_PATH`：

- 调度线程把用例刚启用的订阅源"顺手跑掉"并回写 `next_run` → `due_watches()` 从 1 变回 0。
- 用例的活动任务被它当自己的，在单例 `_active` 里留条目 → 别条用例的看门狗问
  `_owned_by_any_manager(tid)` 得 True 就不敢收；而 tid 在小库上**从 1 重数**，**跨用例撞号**。

**为什么既有隔离管不到**：`tests/isolation.py` 登记的是**路径**；`conftest.py` 顶部记的两轮
污染源都是**磁盘状态文件**。这轮的污染源是**一条进程内线程** + **一个跨用例复用的 dict**。

**定位手法**：写一个 in-process pytest 插件，在 `pytest_runtest_setup` 打印活着的线程 /
`active=` 大小，`-p <插件> -s` 跑一轮。第一动作是**打出实际状态**，不是重跑撞运气。

**修法**（`tests/conftest.py::_muzzle_import_time_singleton`，autouse）：只停**后台循环**
（`_watchdog_stop.set()` / `_scheduler_stop.set()`），**不动方法本身**（有用例直接同步调
`_final_status` / `submit_resource`）；用例结束把 `_active` 的增删抹平。

**副作用是好信号**：全量 **反而快了**（污染那轮 ≈274s → 修复后 183s）—— 杂散线程本来在做无用功。

## 四（2026-09-24 四）：让"绿/红"不再可能是假的

用户问"**假绿/假红你推荐怎么修复**"。答完就直接落地了 —— 因为两类都在本项目真实发生过，
不是假想问题。

### 根因是同一个：判据挂在了错误的东西上

| | 判据挂在哪 | 症状 |
| --- | --- | --- |
| **假绿** | "**没报错**" | 闸跑了、印了 ok，但它**一项都没核**（要核的对象根本不存在）→ 把"没验过"当成"验过了没问题" |
| **假红** | "**中文文案**" | `assert "chrome" not in msg`，而那句文案提到 Chrome 是说它**没用** → 一条**正确**的实现被判红，修的人会去改产品迁就断言 |

### 落地的三处

1. **`add_site.py` 改成结构化的 `Gate`**：`checked` 必填且是实际数目，`0` 一律算红；
   "空转"做成 `Gate` 自己的性质（`effective_problems()`），脚本/`verify()`/测试读同一个判据；
   问题带 `kind`，测试断言代号不断言文案。
   *那条活的假绿*：`check_site()` 在零样本时返回空列表（每条检查都被 `if … and samples:`
   挡掉），于是闸 1 曾把一个**还没写样本的新站点直接放行**。
2. **`diagnose_block` 的建议加 `step` 代号** → 判据变成 `ip[0] != cf[0] and ip[1] != cf[1]`。
   顺手把重试条件从**黑名单**（`kind != "ip_block"`）改成**白名单**
   （`_RETRY_STEPS = ("impersonate", "escalate")`）：黑名单会随新增成因不断漏人，
   429/5xx 原本也各白跑一次换指纹。
3. **`drift_check.py` 一个站点都没查成时退出 2**（原来印"无硬漂移"并 `exit 0`）。
   最坏的一种绿：**把"巡检自己坏了"伪装成"站点没变"**，挂定时任务的人只会一直收到"一切正常"。

### ⚠️ 目视输出抓出的第 20 条（比上面三条都值钱）

```
  => 成因: [cf_challenge] …                    <- 第一遍: 判对了
  => 403: 自动改用 chrome TLS 指纹重试一次(curl-cffi)
  => 成因: [blocked] 403, 但看不出具体成因…     <- 第二遍: 线索丢了
```

根因一步定位：`with session.get(url, stream=True) as resp:` ——
**`curl_cffi.requests.Response` 不支持上下文管理器**（`TypeError: 'Response' object does not
support the context manager protocol`）。这个写法本仓库抄了**三遍**
（`gallery_base._head_status_headers` 的流式回退 / `probe_site.sniff` / `probe_site --smoke`），
**每处都包着 `except Exception`** → 从不报错，只是静默什么都拿不到。

它只在**最需要换指纹的场合**（站点在 CF 后面）出问题，失败又长得像"站点不允许下载"。
真实后果：CF 挑战页被判成"看不出具体成因"，用户丢掉"要去开真浏览器"这条线索。

**修法**：抽 `backend/core/transport.py`（会话工厂 `build()` + 流式请求 `streamed()`，显式
`close()`），三处统一走它。并加一条 **AST 源码门禁**盯着这个写法有没有再被写回去 ——
⚠️ 门禁第一版用正则扫文本，**第一天就红**：它把注释/文档字符串里的反面教材也当违规。
一条一开始就需要豁免的门禁迟早会被加到失效，**判据要落在语法结构上**。

### 同一个错的第二种形态：局部变量遮蔽模块名

`core/transport.py` 一进来，`probe_site.main()` 里 `session, transport = make_session(...)`
就变成了第 13 条的同族（形参/局部名遮蔽）→ 改名 `transport_name`。
**新加 import 之后要回头看一眼有没有同名局部变量** —— 遮蔽是悄悄发生的。

### 一条判据错，连"闸崩了"都能被当成"闸过了"

写 `variants=[]` 的坏声明去试闸 4，闸是**崩**的（`GallerySite.media()` 在 `self.variants[0]`
抛 `IndexError`）而不是报错。崩比报错更糟：脚本跑不完，**前面几道闸已核出的结论一起丢掉**，
而真正的原因一个字也没提。加 `_media_names()` 把异常变成一条能直接照做的问题。
